# Nocturna Base — automation scripts for *Code: Terraform*

A complete, running base written in the game's Python subset: terraforming, power,
mining, smelting, freight and the biology loop, plus the contract puzzles. Wherever
several machines run the same loop, that loop lives in one of twenty-three shared libraries
under `lib/` and the machine script is three lines.

The scripts are written to survive the whole campaign unchanged. Nothing hardcodes a
component id, nothing assumes a research is unlocked, and every optional component —
the Signal Bus, the Data Archive, Auto Feeders, a Mk III fluid port — is probed at
runtime. A base that lacks one degrades to simpler behaviour and says so once at
startup instead of failing on the first call.

## Documentation

Each function also carries a docstring explaining not just what it does but why it is

## Layout

| Path | What it is |
| --- | --- |
| `*.py` | One script per machine or vehicle. Named for the component it runs inside. |
| `panel_*.py` | One script per Control Room card. Draws a dashboard; has `panel`, not `self`. |
| `lib/*.py` | In-game Libraries. Shared loops and helpers, imported by name. |
| `*.pyi`, `pyrightconfig.json` | Type stubs, generated by the game, for editor support. |
| `docs/` | This documentation. |

Two things in a local checkout are deliberately not published: the game's own API
manual, which is the game's content rather than mine, and `codeterraform-scripts.json`,
the save-specific manifest the game owns and regenerates.

A machine script looks like this, and that is the whole file:

```python
import terraform

terraform.run_heater(self)
```

`self` is the machine the script runs inside, injected by the game. Libraries never
touch `self` — the machine is always passed in — because several commands
(`set_power`, `charge`, `dispatch_rescue`, `sync`) are self-only and error when
reached through `get_component()`.

## How the base coordinates

Three mechanisms, each with one job:

- **Libraries** share code.
- **The Signal Bus** shares live values between running scripts.
- **The Data Archive** stores what was learned, across restarts and save/load.

No script drives another. Each publishes what it knows and reads what it needs, so
stopping one degrades the base rather than hanging it.

### Signal Bus channels

| Channel | Published by | Carries |
| --- | --- | --- |
| `power.mode` | `solar_1` | `normal` or `conserve` |
| `power.budget` | `solar_1` | stored, capacity, net, Wh needed to reach dawn, hours to dawn |
| `power.shed` | `solar_1` | which machines the supervisor switched off, and why |
| `power.ledger` | `solar_1` | the night/day ledger, when there is no Data Archive |
| `earth.demand` | `supply_dock_1` | `{item_id: units}` Earth is still waiting for |
| `bio.wanted` | `bio_exchange_1` | fragment ids some open Bio Order still has room for |
| `terraform.heater_table` | any heater | learned `{thermal_state: watts}` |
| `vehicle.status:<id>` | each vehicle | state, battery, position, docked, home, target, plus what only that kind has |
| `rover.claim:<site_id>` | each rover | the rover id working that deposit |
| `bio.*.status` | the three bio machines | heartbeats |

Where staleness matters, readers use an aged read and treat an old value as no value.
A publisher that stops therefore releases the base rather than freezing it: no
`power.mode` means full power.

Two channels are heartbeats for a machine the supervisor can switch off, and switching
a machine off *pauses its script*. Silence there means "nobody is publishing", never
"nothing is wanted", so both have a fallback that reads the source directly: a stale
`bio.wanted` sends the supervisor to the Exchange's own order list, and a stale
`earth.demand` sends `lib/recipes.py` to the Earth Order board.

### Data Archive keys

| Key | Written by | Holds |
| --- | --- | --- |
| `power.ledger` | `lib/power.py` | the grid it was measured on, plus night length, night load and day generation |
| `power.shed` | `lib/power.py` | machines switched off, so a restart can restore them |
| `rover.sites` | `lib/rover.py` | every surveyed mineral site, and whether it is worked out |
| `vehicle.wh_per_meter:<id>` | `lib/vehicle.py` | learned drive cost per vehicle, used to decide range |
| `terraform.heater_optimal` | `lib/terraform.py` | the power setting that reads 100% per thermal state |

## The Control Room

Five script-driven cards on the Control Room page, one script per card, each repainting
every tick:

| Card | Size | Answers |
| --- | --- | --- |
| STATUS | 2x1 | Is anything wrong right now? |
| TERRAFORM | 2x2 | Is the planet actually changing? |
| PRODUCTION | 2x1 | Is the base making things, and how fast? |
| FLEET | 2x1 | Where is everyone and what are they doing? |
| EARTH | 1x1 | What does Earth still want? |

A card is not a machine script. It has no `self`, so no machine action works from it;
it gets `panel` instead. It reads through `lib/readout.py` and draws through
`lib/dash.py`, which is why a card file is a layout and nothing else.

Three rules shape them, and they are the same three that shape everything else here:

- **Nothing is named.** Machines are found through `caps.buildings(type_id)`, which
  walks the whole outpost network, so production moving to its own base grows a second
  outpost heading rather than needing an edit.
- **Staleness is shown, not repeated.** Switching a machine off pauses its script, so its
  bus channel keeps its last value while nothing is publishing. Every bus read on a card
  is aged; a vehicle whose script has stopped is marked `stale` rather than shown the
  verb it published minutes ago.
- **The board reads; it does not command.** Cards *can* reach `power_control`, but
  `lib/power.py` is the single owner of breakers. Two writers on one concern is worse
  than none, so an operator override belongs on a bus channel the supervisor obeys.

## Installing into your own save

This folder *is* a save's script folder. On Windows it lives at:

```
%APPDATA%\io.codeterraform.game\save_<save id>_scripts
```

The game keeps that folder in sync with its own editor through a manifest it owns, so
the reliable way to adopt these scripts is through the game rather than by dropping
files in: create a Library with the matching name for each file in `lib/`, then a
script on each machine, and paste the contents in. Library names must match the
imports — `bus`, `caps`, `rover` and so on.

Machine scripts are named after their component id (`heater_1.py` runs on `heater_1`).
Your save's ids will differ; the file contents do not care, because every id a script
uses is discovered at runtime rather than written down.

## Research gates

Everything degrades gracefully, but some things simply cannot work yet:

| Research | Without it |
| --- | --- |
| Signal Bus | Scripts still run; they just stop coordinating. Local fallbacks apply. |
| Data Archive | Learned values live only in the running script and the bus. |
| Auto Feeders | Machine `.input` / `.output` ports do not exist. The smelter, dock, bio loop and rover unload halt with one clear message. |
| Supply Logistics | No Supply Dock. |

Drill, sonar and nav modules are per-vehicle equipment rather than research, and the
rover reports its drill hardness and sonar tier at startup.

## House rules

The conventions every file follows, worth knowing before editing one:

1. **Discover, never hardcode.** Component ids are not guessable, and a wrong id
   behaves exactly like a full bin or an empty bank. `caps` and `storage` find things.
2. **Probe, never assume.** `get_component()` returning `None` is a normal answer.
3. **Branch on `.status`, never on `.message`.** Status strings are stable; messages
   are localised prose. `lib/results.py` names the common groups.
4. **One publisher per channel.** Two writers on one channel is worse than none.
5. **Say it once.** A script that is blocked explains why on its first pass and then
   stays quiet, rather than repeating a warning every ten seconds.
6. **Get near, park, then work.** Reaching a target's tolerance means close enough,
   not stopped. `nav.brake()` comes before every scan, survey, drill or transfer.

## Editor support

`pyrightconfig.json` points Pylance at the stubs in this folder, which gives real
completion and diagnostics for the game API. One diagnostic is expected and cannot be
fixed: `"self" is not defined`, in every machine script, because the game injects
`self` at run time. Everything else should be clean.

The `.pyi` files are generated by the game and derived from typeshed; see
`typeshed-LICENSE.txt`. Do not edit them. `user_stubs.py` is the file the game never
overwrites, and is the place for your own type aliases.
